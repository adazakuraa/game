## 0. 依頼と現状

### 0.0 トラッカー Phase 8（原文）

1. 現状の魚・生物モデルはコード生成の簡易モデルで、お粗末で現実の魚から程遠い。見た目を現実の魚に近づけるよう刷新する。
2. 実機で動作が重い（2026-11-25 ユーザー実機報告）。見た目刷新とあわせて、ドローコール・インスタンシング・解像度スケーリング・読み込みサイズの見直しで軽くする。
3. 目標水準は写真そのものではなく、シルエットと動きが本物らしく見える水準とする。スマホの描画負荷を最優先する。
4. 近景の主役となる魚は、CC0など無料で再配布可能な3Dモデルの活用を検討する。そのままでは重い場合は、ポリゴン削減・テクスチャのベイク・glTF化でスマホ向けに軽量化する。
5. 3Dモデルが使えない魚は、生成モデルの作り込みで対応する。体の断面プロファイル、ヒレの形状、模様、泳ぎのうねりを実物に近づける。
6. 遠景の魚は簡易モデルや写真スプライトで数を稼ぎ、近景にだけ描画コストをかけるLODの使い分けをする。
7. 使用するアセットは無料かつ再配布可能なライセンスのものに限る。出典とライセンスは CREDITS.md に記録する。有料アセット・有料APIは使わない。
8. アセットの取得・加工（軽量化）とライセンス確認は Muse が担当し、ゲーム内への組み込みとアニメーション調整は Claude が担当する分担を前提とする。
9. マテリアルとライティング（PBR、水中らしい光の表現）もあわせて見直し、モデルの刷新効果を底上げする。

## 1. LOD の構成

### 1.1 段（決定）

| 段 | 対象 | 切り替え（画面上の体の高さ） | 中身 | 三角形の上限 |
| --- | --- | --- | --- | --- |
| **L0 近景** | 画面で大きい個体 | 120px 以上 | 主役 3D モデル（§2）／写真魚／生成魚 v2 の高精細 | 生成魚：体長 0.4m 未満 1,500、以上 2,500。写真魚 2,240（現状維持）。3D モデル 4,000（サメ・エイ・ジンベエ・カメは 6,000） |
| **L1 中景** | 中くらい | 24〜120px | 同じ種の簡易版（同じテクスチャ・同じ UV） | 400（写真魚は列 20×行 8＝640） |
| **L2 遠景** | 小さい点 | 24px 未満 | **写真スプライト**：全種共通の 1 つの InstancedMesh（アトラス）に入れた横向きの絵 1 枚 | 2（縦に 3 分割して曲げる場合 6） |
| 非表示 | 霞の外 | 現行の距離切り（`writeInstance` の 20／34／46／52+3s m）と視野外判定 | — | 0 |

- 画面上の高さ `hpx = s × hRatio × focalPx / d`（`s`＝体長、`hRatio`＝体高/体長、`focalPx = 画面の高さ px / (2·tan(fov/2))`、`d`＝カメラ距離）。距離ではなく画面上の大きさで切るので、ジンベエザメは遠くても L0、ハゼは近くても L1 になる。端末の解像度が違っても見た目が揃う。
- ヒステリシス 15%（上がるときは 120／24、下がるときは 102／20）で、境目でちらつかない。
- 撮影中（シャッター準備中の照準対象 `findTarget` の 1 位）と `pin`／`companion`／`stage` の個体は常に L0（写真の評価画像 `takePhoto` は L0 で撮る）。

### 1.3 既存の仕組みをどう伸ばすか（作り替えない）

- `SpeciesRuntime.mesh`（1 つ）を `mesh`（L0）＋`mesh1?`（L1）に広げる。**マテリアルは L0・L1 で共有**（同じテクスチャ・同じシェーダ、ジオメトリだけ別）。ジオメトリは同じビルダーを `detail` を変えて 2 回呼ぶ（UV は平行投影なので両方で一致する）。
- `buildMesh` の遅延生成・6ms 予算はそのまま。L1 は L0 と同時に作る（ジオメトリ生成は 1ms 未満、テクスチャ描画が重いのは L0 と共有）。
- `writeInstance` は今「画面内・近い個体を詰めて `mesh.count` で切る」。これを「段を決めて、その段のメッシュのスロットに詰める」に変える（`rt.slot` を `rt.slot0`／`rt.slot1` に、L2 は共有アトラスのスロットへ）。距離切り・視野外判定・`maxDrawn = 70`（近い順に描く種数の上限）は残す。L2 の個体は `maxDrawn` の数え方から外す（共有の 1 呼び出しなので）。
- 新設：`src/life/impostors.ts`（L2 の共有 InstancedMesh とアトラス）。アトラスは 2048×1024 の 1 枚、1 コマ 128×64（256 種分）。種のコマは `buildMesh` のときに描く（生成魚は `Paint` の canvas をシルエットでクリップして縮小、写真魚は写真をそのまま縮小、3D モデルはオフスクリーンの側面描画）。コマがいっぱいになったら古い順に再利用（§6.3-⑥ の破棄と連動）。
- L2 のカードは **体の長さ方向の軸のまわりだけ回してカメラに向ける**（軸固定ビルボード）。正面から見ると細くなるので、本物の魚と同じように見える。泳ぎのうねり（§4）は同じ式をカードの頂点にかける（縦 3 分割のとき）。
- 段ごとの個体数は `__THREE_GAME_DIAGNOSTICS__.creatures` に `l0/l1/l2` として出す（§10）。

## 2. 近景の主役 3D モデル

### 2.1 採用基準（決定）

1. **ライセンス**：CC0 またはパブリックドメイン、もしくは再配布・改変・商用を許すライセンス（CC BY は CREDITS.md の表記で可）。Muse がダウンロードした元ファイルとライセンス文を確かめたもの。**AI 生成の素材は §2.6 の条件を満たすまで公開版に入れない**（AW）。
2. **種が合う**：ゲームの種と同じ種（できれば）。同属で見た目が区別できないもの（体型・ヒレ・模様が同じ）なら可。別属は不可（図鑑の写真の名前と食い違うため）。
3. **よく近くで見る種**：撮影対象として 3m 以内に来ることが多く、体長 0.3m 以上、またはストーリー・光景・依頼に出る種。小魚の群れは L1／L2 がほとんどなので対象外。
4. **予算に入る**：加工後に §1.1 の三角形上限、§2.3 のファイルサイズに入る。
5. **曲げ試験に通る**：§2.4 のうねりをかけて、ヒレや体表が裂けない・つぶれない（§10.3 の目視）。

候補の当てはめ（監督の候補リストとゲームの種の照合）：

| 候補（パック） | ゲームの種 | 判断 |

### 2.2 加工の手順（Muse）

1. 元ファイルをダウンロードし、ライセンス文を保存（§7.2）。
2. Blender（ヘッドレス）か gltf-transform で：
   - 向きと大きさを揃える：**頭が +Z、背が +Y、体長（吻端〜尾端）1.0、体長の中点が原点**。左右対称面が x = 0。ゲームの生成モデルと同じ約束なので、`def.size`（体長）がそのままインスタンスの拡大率になり、泳ぎの式（§4）も同じものが使える。
   - メッシュ 1 つ・マテリアル 1 つに結合。目・歯などの別パーツも結合する。リグ・アニメーション・カメラ・ライトは消す。
   - ポリゴン削減：LOD0 を §1.1 の上限（4,000／大型 6,000）まで。**体の長さ方向に 24 本以上の輪（エッジループ相当）が残るように**する（頂点シェーダで曲げるので、長さ方向の頂点が粗いと尾が折れ線になる。目安：体の部分で z 方向の辺の長さ ≤ 0.04）。LOD1 は 600 三角形まで、**LOD0 と同じ UV 配置**を保つ（同じテクスチャを共有するため）。
   - テクスチャのベイク：ベースカラー 1 枚（512×256、模様の細かい種でも 512×512 まで）。法線マップは 256×128 まで任意。粗さ・金属度はテクスチャにせず数値（`def.mat` で持つ）。AO はベースカラーに焼き込む（水中の柔らかい光で、焼き込み AO が一番効く）。
   - 頂点カラー `COLOR_0`：R＝ヒレの膜（1＝膜、0＝体。透け・ヒレ用の光り方に使う `aFin` になる）、G＝羽ばたきの重み（胸ビレ・カメのヒレ。`aFlap` になる）、B＝未使用（0）。塗れない場合は全部 0 で渡してよい（§2.4 の自動推定に落ちる）。
3. 書き出し：GLB、`KHR_mesh_quantization`（位置 16bit・法線 8bit・UV 16bit）、`EXT_meshopt_compression`、テクスチャは `EXT_texture_webp`（q80）。Draco は使わない（復号器が wasm で大きく、単一 HTML に向かない）。
4. 検品：three.js の公式ビューア（gltf-viewer）で表示できること、三角形数・大きさ・向きの確認、§2.3 のファイルサイズ以内。

### 2.3 単一 HTML への埋め込み（Claude）

- 置き場所：`src/assets/models/<種id>.glb`（LOD0）と `<種id>.lod1.glb`。`photoFish.ts` と同じく `import.meta.glob('../assets/models/*.glb', { eager: true, query: '?url', import: 'default' })` で取り込む。Vite の `assetsInlineLimit` は既に十分大きいので data URL として JS に入る。
- 読み込み：`three/addons/loaders/GLTFLoader.js` と `three/addons/libs/meshopt_decoder.module.js`。`buildMesh` で data URL を `fetch` → `ArrayBuffer` → `GLTFLoader.parseAsync`。**非同期**なので、モデルが届くまでその種は生成モデル（または写真魚）で描き、届いた時点で差し替える（初回の遅延なし）。
- 取り出し：シーンの最初のメッシュのジオメトリとベースカラーを取り、`aBend`（z から §4 の式で計算）、`aFin`（COLOR_0.R）、`aFlap`（COLOR_0.G）、`aPulse`・`aGlow`（0）を付けてから、既存の `makeMaterial`（`PHOTO_FISH` と同じ扱いの define `HERO_MODEL`：模様はテクスチャにある、鱗のシェーダは入れない）に渡す。InstancedMesh・遅延生成・LOD の仕組みは写真魚と同じ流れ。
- 大きさの予算：1 種あたり GLB 2 本で **合計 55 KB 以内**（ジオメトリ 15〜25 KB＋WebP 25〜35 KB の見込み）。最大 6 種で 330 KB（base64 で約 440 KB）。ローダーと復号器のコードは約 70 KB 増える見込み。§6.4 の表に入れた。
- 対応表：`src/life/heroModels.ts` に `HERO_MODELS: Record<種id, { lod0: string; lod1?: string; rough?: number; metal?: number }>`。**表にない種は従来どおり**（採用は種ごとに任意）。

### 2.4 泳ぎの仕組みは輸入モデルにもそのまま効く

- 頂点シェーダのうねりは「位置の z だけで決まる重み `aBend`」と「体の座標系（+Z 前、x 横）」に依存しているだけなので、§2.2 の向き・大きさの約束を守れば、リグのない静的メッシュにも同じ式がかかる。`aBend` は読み込み時に z から計算するので Muse の作業はいらない。
- `COLOR_0` がない場合の自動推定：`aFin` は「その z での体の断面の幅に対し、頂点の |x| が 15% 未満で、かつ体の上下の包絡線より外」（ヒレの膜）を 1。`aFlap` は 0（胸ビレは動かない）。
- 曲げ試験（§10.3）で破綻する場合の代わり：(1) 曲げの振幅をその種だけ下げる（`def.swim` で上書き）、(2) それでも駄目なら採用しない（§2.5）。骨入りのスキニングは入れない（スマホの負荷とファイルサイズが増え、613 種の仕組みと別系統になるため）。

### 2.5 写真魚の拡大（もう 1 つの主役ルート）

- 既存パイプライン `scripts/photo_fish.py`（Wikimedia Commons の PD／CC0 写真）で、写真魚を **31 種 → 約 60 種**に増やす。写真魚は 1 種 15〜25 KB で一番「本物らしさ」の割がよく、加工が自動化されている。
- 新しく足す分は書き出しを **幅 448、WebP q75**（既存 512・q82 から）にして平均 16 KB 以内（§6.4 の予算）。既存 31 種は、`photo_fish_picks.json` が元画像のパスを持っていない（候補番号 `i` だけ）ため、パイプラインを回し直さず**今の WebP を 448 幅・q75 に再エンコード**する（輪郭の profile は変わらない）。見た目の差は §10.3 で確認し、劣化が目立つ種は元のまま。
- 優先順：体長 0.3m 以上の魚 234 種のうち、(1) 撮影依頼・章・光景に出る種、(2) よく出る（rarity 1〜2・個体数が多い）種、(3) 体型テンプレートで似せにくい種（ハタ・ベラ・タイ・アジ類）。Muse が写真を探し、側面・ヒレが開いている・水平に近い・切り抜きやすい背景の写真を選ぶ。
- 3D モデルの採用が失敗した種の戻し先も写真魚（写真がなければ生成魚 v2）。

### 2.6 AI 生成素材（Polyy.AI パック）の扱い（AW）

プロジェクトの「公開版は著作権的にきれいであること」に照らすと、AI 生成の素材は次の点が確かめられないうちは使えない：

1. 配布者が誰で、CC0 の宣言がページに明記されているか（ストアの説明文だけでなく、同梱のライセンス文）。
2. 生成に使ったツールの利用規約が、出力の CC0 配布と商用利用を許しているか。
3. 特定の写真・作品・既存モデルの写し（学習元の再現）でないか。

確かめられた場合だけ、他の素材と同じく §2.1 の基準で 1 種ずつ採用する。確かめられない間は **社内の参考（形・解像度・三角形数の比較用）に留め、公開版にもリポジトリにも入れない**。CREDITS.md には「AI 生成」である旨と生成ツール名も書く（採用した場合）。

## 3. 生成モデル v2（3D モデルのない魚）

体型テンプレート `B`（57 体型、229 種）と個別定義（約 227 種）の `FishShape` を入力に、`buildFish` と `paintLook` を直す。**新しい項目はすべて省略可で、省略時は体型ごとの既定値**（体型の既定値は species2.ts の `B` に足す）。個別定義の種は既定値で自動的に良くなる。

優先順は「見た目の効き目 ÷ 手間」で決めた（P1 が最優先）。

### 3.1 P1 断面と横幅の包絡線（決定）

今：断面は楕円（x にだけ `1 − 0.15·cos` の補正）、横幅 W と高さ H に**同じ包絡線 `env(t)`** を掛けている。そのため尾柄（尾の付け根）が体と同じ比率で太く、魚が「ふくらんだ筒」に見える。

- **横幅専用の包絡線 `wEnv(t)`**：頭から最大幅（`wPeak`、既定 0.6〜0.7）まで太り、尾柄で `pedW`（既定 0.3 × 体の最大幅）まで急に細る。頭部の横幅 `headW` は既存項目をこの包絡線の中で使う。
- **断面のかど `xs`**（スーパー楕円の指数、既定 2.0）：側扁した体（チョウチョウウオ・ハギ・アジ）は 2.4〜2.8 で体側が平らに、円筒形（ハゼ・ボラ・サメ）は 2.0。
- **腹と背の非対称**：背中を高く腹を丸く（既存の `belly` と `hump` に加え、断面の上半分・下半分で指数を変える `xsTop`/`xsBot`）。
- **竜骨**：マグロ・アジの尾柄の横の隆起（`keel`、0〜0.3）。
- 分割数：L0 は rings 16・segs 28（小型）／rings 18・segs 32（0.4m 以上）。L1 は rings 8・segs 12。断面の分割が 8 だと近くで八角形に見えるのが今の弱点。

### 3.2 P2 ヒレの形と動き（決定）

今：ヒレは `ShapeGeometry`（外形の点だけで三角形分割）を 2 枚重ねた板。内部に頂点がないので、うねりで曲げると大きな三角形のまま動き、尾びれが平行移動するだけに見える。

- **ヒレを格子で作る**：外形の内側を「付け根→縁」方向 4 段 × 長さ方向 n 列の格子にする（三角形は 1 枚あたり 30〜80）。曲げ・羽ばたき・透け（縁ほど薄い `aFin` 1.0〜1.49）が滑らかになる。
- **尾びれの形を曲線で**：二叉（fork）は上下の葉を弓なりに、湾入（lunate）は三日月の先を細く、円形・截形は縁をゆるい曲線に。既存の `tail`・`tailL`・`tailH` の意味は変えない。
- **背びれ・臀びれ**：棘のあるヒレ（`jag > 0`）は棘の間の膜を縁で凹ませる（今は高さを交互に下げるだけ）。軟条部と棘条部の高さの段差（`dorsal` を 2 つ並べている体型はそのまま）。
- **胸びれ**：扇形（根元が狭く先が丸い）にし、付け根まわりに回転する羽ばたき（`aFlap` の重み）を付ける。ベラ・ブダイ・ハコフグ・フグのように**胸びれで泳ぐ体型**（§4.2 の `labriform`）ではこれが主な動きになる。
- **腹びれ**：今の 4 点の三角に近い形を、胸びれと同じ扇形の小型版に。

### 3.3 P3 頭・目・口（決定）

- **目**：今は 8×6 の半球をつぶしたもの。12×10 の球にし、表面の 70% を体に埋めて角膜の丸みだけ出す。角膜は `aFin = 2`（なめらか、粗さ 0.06）で既存のまま、瞳と虹彩はテクスチャ（`Paint.eye`）で描き、球の正面に UV を合わせる（今は側面投影の UV なので目玉の絵が引き伸ばされている）。
- **口**：`mouth?: 'term' | 'sup' | 'inf'`（端位・上向き・下向き、既定は体型ごと）。吻の先端の包絡線を上下にずらして口の位置を作り、口の切れ込みは頂点を少し内側へ押した溝＋テクスチャの線（`Paint.mouth`）。
- **鰓蓋**：テクスチャの線（既存 `Paint.gill`）に加えて、鰓蓋の縁で法線を少し曲げる（シェーダの `uwBump` に鰓蓋の線の高さを渡す）。形を変えずに光の当たり方だけで段差が出る。

### 3.4 P4 模様（paint.ts）（決定）

- **ぼかし**：帯・斑点・網目の縁を `ctx.filter = 'blur(…)'`（テクスチャ幅の 0.3%）で柔らかくする。本物の魚の模様は縁がにじむ。今はすべて硬い縁。
- **側線**：体型ごとに側線の高さの曲線を持たせ、細い明るい線を描く（`Look.lateral?: boolean`、既定は鱗の目立つ体型で true）。
- **鱗**：シェーダの鱗模様（`fishScale`）は UV で一様な格子（58 列）。体の大きさに関係なく同じ数になるので、体型ごとに鱗の列数（`scaleN`、ボラ 40・マダイ 60・ハゼ 30 など）を持たせ、行を体の包絡線に沿わせる（v を `y / env(t)` で正規化）。
- **ヒレの色**：ヒレの縁の色（`Look.finEdge`）と軟条の筋をテクスチャ側にも描く（今はシェーダの縞だけ）。
- **反射の強さの地図**：テクスチャの α チャンネル（生成魚では今は使っていない）に「銀色に光る部分」（腹・体側の銀白色）を描き、§5.2 の体側の反射に使う。`Look.sheen?: number`（既定は `mat.metal` から）。

## 4. 泳ぎ・動き（シェーダの方式のまま）

### 4.1 今の問題（コード）

1. **せん断になっている**：`transformed.x += wave·amp·aBend` は頂点を横へずらすだけで、断面が背骨の傾きに合わせて回らない。尾びれが「横へ滑る板」に見え、体は「ゴムのようにずれる」。
2. **速さと尾の振りが無関係**：周波数 `uSwim.x` と振幅は種ごとの uniform で、逃げて速く泳いでも、止まって漂っていても同じリズム。
3. **曲がるとき体が曲がらない**：向きは `orient` で丸ごと回すだけ（C 字に曲がらない）。
4. **振幅の分布**：`bendW(z) = ((0.5 − z)/1)^1.6 × 0.95 + 0.05`、波数 k＝4 前後、振幅 0.04〜0.05 L。魚の泳ぎ方の違い（ウナギ型・アジ型・マグロ型・胸びれ型）がない。

### 4.2 決定

- **背骨の線で曲げる**：頂点 (x, y, z) の背骨の横ずれ `o(z, t)` とその傾き `θ = atan(∂o/∂z)` を解析的に求め、`x' = o + x·cosθ`、`z' = z − x·sinθ`（BEND_Y の種は y で同じ）。法線も θ だけ回す。尾びれは背骨に垂直なまま振られるので「水をかく板」に見える。計算は sin/cos が数回増えるだけ。
- **泳ぎ方の型 `swimMode`**（体型の既定値。species2.ts の `B` に足す、個別定義の種は kind・体型から自動）：

| 型 | 振幅の分布 A(s)（s＝0 頭 … 1 尾、体長比） | 波長 | 尾の振幅 | 例 |
| --- | --- | --- | --- | --- |
| anguilliform（ウナギ型） | 0.04 + 0.04s | 0.6 L | 0.08 | ウツボ・アナゴ・チンアナゴ・ヤガラ |
| subcarangiform（標準） | 0.02 − 0.08s + 0.16s² | 1.0 L | 0.10 | 大半のサンゴ礁魚・ハタ・タイ |
| carangiform（アジ型） | 0.01 − 0.05s + 0.14s²（前半ほぼ動かない） | 1.1 L | 0.09 | アジ・カツオ以外の回遊魚・バラクーダ |
| thunniform（マグロ型） | 尾柄から後ろだけ（s > 0.75） | 1.2 L | 0.08 | マグロ・カツオ・サメ類（サメは尾を BEND_Y にしない、横振り） |
| labriform（胸びれ型） | 0.01（体はほぼ止める） | — | 0.02 | ベラ・ブダイ・フグ・ハコフグ・ハギの一部。胸びれの羽ばたきが主 |
| 現行のまま | — | — | — | エイ・クラゲ・イカ・タコ・カメ（専用の動き） |

（係数は Videler の実測曲線に近い形。尾の振幅は片振幅、体長比。最終値は §10.3 の目視で調整する）

- **個体ごとの属性**：`InstancedBufferAttribute` を 1 つ足す `aSwim = vec4(phase, ampK, turn, flapPhase)`（1 個体 16 バイト、`writeInstance` で毎フレーム書く。今の行列 64 バイトに比べ小さい）。
  - `phase`：CPU で積算する `a.swPh += 2π·f·dt`。**周波数を個体の速さから決める**：`f = clamp(f0 + U / (0.7·L), fMin, fMax)`（U＝速さ、L＝体長、0.7 L＝1 回の振りで進む距離の目安）。見た目のため `fMin` 0.6Hz・`fMax` 4Hz（小魚の実際の 10Hz 超は速すぎて震えに見える）。積算なので速さが変わっても位相が飛ばない。
  - `ampK`：速さに応じて 0.6〜1.0。`labriform` と止まり気味の個体は「振って→滑る」（0.4〜1.2 秒の滑空で ampK → 0.15）を CPU の小さな状態で入れる。
  - `turn`：直前フレームからの向きの変化率（rad/s、±2 で頭打ち）。背骨に C 字の曲げ `κ·turn·(s − 0.35)²` を足す。急な逃避（`dPlayer < fr` の逃走開始）では 0.2 秒だけ強くする（C スタート）。
  - `flapPhase`：胸びれの羽ばたき（labriform の主動作、他は 0.3 倍）。
- 今の `ph = instanceMatrix[3]…`（位置から作る位相）は `aSwim.x` に置き換える（位置が変わっても位相が変わらないので、泳いでいる間に波が早送りされない）。
- 写真魚・3D モデルにも同じ式がかかる（`aBend` が z から決まるため）。写真魚は板に近いので、tail の振幅を 0.8 倍にする。
- L2 のカード（§1.3）は縦 3 分割のときだけ同じ曲げ。2 三角形のときは曲げない（遠くて見えない）。

## 5. マテリアルとライティング

コードを読んで「今リアルさを抑えているもの」と判断したもの。形と動き（§3・§4）より効き目は小さいので、範囲を絞る。

### 5.1 今の状態

- 生き物は `MeshStandardMaterial`＋`underwaterMaterial`（`creatures.ts` `makeMaterial`）。太陽の平行光（影あり）・半球光・環境マップ（空のグラデーションの PMREM）。環境光の強さは `0.22·exp(y/25)` で、水深 10m で約 0.15、30m で 0.07。
- 追加の表現：水の後方散乱の縁の光（rim）・ヒレの透け・鱗の凹凸（生成魚）・写真の明るさを凹凸に（写真魚）・コースティクス（2 回計算）・霧（距離で水の色に）。
- 弱いところ：
  1. **銀色の魚が灰色に見える**：アジ・イワシ・ボラ類は `metal 0.3〜0.6`・粗さ 0.28 だが、反射する環境（PMREM）が暗く小さいので、体をひねったときの「ぎらっ」が出ない。本物の水中写真で一番目立つ光り方。
  2. **体の下側が明るすぎる／平板**：半球光の地面色が一様で、胸びれの下・腹・ヒレの付け根の陰りがない（自己遮蔽がない）。
  3. **写真魚**：写真の陰影を `flat 0.55` で平らにしているので、近くで見ると立体感が弱い（仕様どおりだが、§3 の形の改善と釣り合わない）。
  4. 霧の色の吸収（赤から消える）は `fogFactor × 0.8` の一律の色味で、距離による色の抜けは出ている。ここは変えない。

### 5.2 決定（範囲）

- **体側の反射（sheen）**：水面方向（上）からの光を鏡のように返す項をフラグメントに足す。`spec = pow(max(dot(reflect(-V, N), up), 0), 8) × sheen × uSunCol × exp(y/25)`。`sheen` は §3.4 のテクスチャ α（生成魚）、写真魚と 3D モデルは `def.mat.metal` から。種ごとの調整項目は増やさない。
- **頂点の陰り（焼き込み AO）**：生成魚は作るときに頂点ごとの陰り（断面の下側・ヒレの付け根・胸びれの陰）を計算し、既存の `aGlow` と同じく属性 `aAO`（0.55〜1）で持って拡散光に掛ける。3D モデルはテクスチャに焼き込み済み（§2.2）。
- **写真魚の平らさ**：新しく足す写真魚は `photo_fish.py` の `flat` を 0.55 → 0.4（陰影を少し残す）で書き出す。種ごとに設定で持つので目視で戻せる。既存 31 種は元画像がリポジトリにないので、Muse が元画像を取り直した種だけ同じ設定で書き直す。
- **やらないこと**：屈折・本格的な表面下散乱・リアルタイムの環境マップ（スマホの負荷が大きい）。地形・植生の PBR は Phase 8 では触らない（性能のための変更 §6.3 を除く）。

## 6. 性能

### 6.1 予算（決定）

対象：スマホの中位機、**30fps を安定**（1 フレーム 33ms）、余力があれば 60fps。数値はサンゴ礁（今いちばん重い地点）での 1 フレーム。

| 項目 | 今 | 予算 |
| --- | --- | --- |
| キャンバスの画素数（スマホ） | 49 万（viewport あり）／**468 万**（viewport なし） | **最大 90 万、通常 49 万前後、下限 30 万** |
| 描画呼び出し（影なしフレーム） | 201 | **≤ 140** |
| 描画呼び出し（影ありフレームの合計） | 269 | **≤ 175**（影パス ≤ 35） |
| 三角形（影なし） | 622k | **≤ 350k** |
| 三角形（影パス） | 269k | **≤ 100k** |
| 生き物の描画呼び出し | 60〜71 | ≤ 50（L2 は全種で 1） |
| 生き物の三角形 | 88k〜120k | ≤ 90k（§3.5 の見込み 7 万） |
| 生き物の CPU（この VM の値） | 2.2ms | ≤ 1.5ms |
| 生成済みの種（同時に保持） | 増え続ける（最後は 510 種） | **≤ 120 種**（古いものから破棄） |
| テクスチャの GPU メモリ（推定） | 61MB（サンゴ礁）、回るほど増える | ≤ 40MB、うち生き物 ≤ 20MB（アトラス 8MB 込み） |
| シェーダプログラム | 30→51（初見でコンパイル） | 潜る前にまとめてコンパイル、潜水中の新規 0 |
| 単一 HTML の大きさ | 4,137 KB | **上限 4,500 KB、設計値 4,400 KB**（§6.4） |

### 6.2 重さの原因（計測から、効き目の大きい順の見立て）

- **H1 画素数**：`play.html` に viewport がない → 980px レイアウト → 画素 9.5 倍。全フレームの全フラグメント（コースティクス 2 回・霧・影の PCF・鱗の凹凸）に効く。アーティファクト版に viewport が付いているかは外枠次第で、ヘッドレスでは確かめられない（AY）。さらに、viewport が正しくても DPR だけの制限なので、大画面のタブレットでは画素が増える。
- **H2 影パス**：浅場（45m まで）でスマホは 2 フレームに 1 回、植生 153 呼び出し・地形 33 チャンクを影マップ（1024²）に描き直す。サンゴ礁で +68 呼び出し・+269k 三角形。
- **H3 植生の三角形と呼び出し**：サンゴ 1 個 832〜880 三角形が 70m 四方のセルごとにまとめて描かれ、セル単位の距離切り（85m）しかない。遠いサンゴも近いサンゴも同じ細かさ。
- **H4 フラグメントの重さ**：全マテリアルがコースティクスを 2 回（各 4 回の三角関数ループ）計算する。影の PCF、霧の方向計算も全画素。
- **H5 小物の呼び出し**：宝箱・拾い物の部品ごとの Mesh と光芒で 61 呼び出し（三角形はほぼ 0）。
- **H6 生成済みの種が溜まる**：破棄しないので、潜っている時間とともにテクスチャ・ジオメトリが増える（GPU メモリ不足の端末では急に重くなる・落ちる）。
- **H7 生き物の CPU**：近くの種の全個体を毎フレーム更新。遠い個体まで同じ頻度。
- **H8 初見のシェーダコンパイル**：新しい種類の生き物・植生に出会うとプログラムが増え、その瞬間に引っかかる。
- **H9 読み込み**：4.1MB のうち 72% が画像の base64。テクスチャの圧縮が甘い（`sand.webp` 348 KB、JPEG は高品質設定）。

### 6.3 手法（効き目の見込みの大きい順）

| # | 手法 | 対象 | 見込み |
| --- | --- | --- | --- |
| ⓪ | **画素数の上限**：`setPixelRatio` を「`min(dprCap, sqrt(90万 / (CSS幅×CSS高さ)))`」にする。適応の段階を 0.15 刻みにし、下げる条件を「平均 > 36ms」、上げる条件を「平均 < 24ms が 3 回続いた」に（30fps 付近で張り付かない）。下限は画素数 30 万相当。あわせて `play.html` の書き出しで `<meta charset="utf-8">` と `<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">` を足す（アーティファクト用の出力は今のまま）| H1 | viewport なしの環境で画素 1/5〜1/9。ありでも大画面を抑える |
| ① | **影を落とすものを絞る**：植生は「カメラから 30m 以内のセル」だけ `castShadow`（セルを 70m → 35m に細かくする。③と共通）、地形は自分のいるチャンクと隣だけ、生き物は「体長 0.6m 以上かつ 20m 以内」。影のカメラの範囲も 30m に合わせて狭める（同じ 1024² で影が細かくなる） | H2 | 影パス −40〜50 呼び出し、−170k 三角形 |
| ② | **植生の遠景 LOD**：`ScatterSet` には既に「近いときだけ細かいジオメトリ」の仕組み（`hiGeo`/`hiDist`）がある。これを「25m より遠いセルは 1/4 の三角形の簡易ジオメトリ」にも使う（サンゴのビルダーに分割数の引数を足して 2 回作る）。セルを 35m に分けて、遠いセルほど簡易に | H3 | 三角形 −250k〜350k（サンゴ礁）。呼び出しはセル分割で一時的に増えるので、③の遠いセルの統合で相殺 |
| ③ | **フラグメントを軽く**：スマホではコースティクスを 1 回（2 回目を省く）、生き物は L1・L2 でコースティクスなし、`FISH_SCALES` の凹凸は L0 だけ（define で分ける）。影の PCF はスマホで 1 サンプルの `BasicShadowMap` 相当（`shadow.radius` を使わない） | H4 | フラグメント 2〜3 割減の見込み（実機で確認） |
| ④ | **小物をまとめる**：宝箱・拾い物・依頼の箱は部品をジオメトリ結合して 1 個 1 呼び出しに、さらに 60m より遠いものは描かない。光芒 19 枚は 1 つのジオメトリに結合 | H5 | −50 呼び出し前後 |
| ⑤ | **生き物の LOD と共有アトラス**（§1）：遠景の種は 1 呼び出しにまとまる。L0 の種数は画面上の大きさで自然に絞られる | 呼び出し・三角形 | 生き物の呼び出し 60 → 40 前後 |
| ⑥ | **生成済みの種を破棄**：種ごとに「最後に近くにいた時刻」を持ち、保持数が 120 を超えたら 90 秒以上離れている種から `geometry.dispose()`・`material.dispose()`・テクスチャ `dispose()`（アトラスのコマも返す）。また近づけば遅延生成でまた作る | H6 | メモリが潜水時間で増えなくなる |
| ⑦ | **遠い個体の更新を間引く**：ダイバーから 25m より遠い個体は 2 フレームに 1 回、45m より遠いと 4 フレームに 1 回（dt をまとめて渡す）。逃走中・追従中・撮影対象は毎フレーム | H7 | 生き物の CPU 3〜4 割減 |
| ⑧ | **シェーダの事前コンパイル**：潜る前（ボート画面→潜水の暗転中）に、その地点で出会う種類のマテリアル（生き物の kind×写真×透け×L0/L1 の組み合わせ、植生）を `renderer.compileAsync` でまとめてコンパイルする | H8 | 潜水中の引っかかりをなくす |
| ⑨ | **読み込みサイズ**（§6.4） | H9 | 4,137 → 3,350 KB（素材追加前） |

①〜④は見た目をほとんど変えずに効くので、見た目の刷新より先に入れる（§9 の手順 S1）。

### 6.4 読み込みサイズの予算（決定、base64 込み）

## 8. 暫定決定（トラッカー未解決事項へ AW〜BH として追記）

- **AW**：AI 生成の素材（Polyy.AI の 3D Fish Pack）→ 暫定：配布者・CC0 の明記・生成ツールの規約・学習元の写しでないこと（§2.6）が確かめられるまで公開版にもリポジトリにも入れない。比較の参考に留める。最初の 3D モデルの試験は THEUNSEENVULGA の素材（`turtle`・`aoriika`）と写真魚の拡大で行う
- **AX**：「重い」がフレームの重さか読み込みの重さか → 暫定：両方を扱い、効き目が大きく見た目を変えないフレームの側（S0・S1）を先に入れる。S0 の診断表示で実機の数値をもらってから S1 の優先順を見直す
- **AY**：`play.html` に viewport がない件 → 暫定：`play.html` の書き出しにだけ `<meta charset>` と `<meta viewport>` を足す（アーティファクトの外枠が付ける前提は変えない）。アーティファクト版にも効くよう、画素数の上限（90 万）はレンダラー側で必ずかける
- **AZ**：LOD の切り替え → 暫定：画面上の体の高さで、L0 ≥ 120px・L1 24〜120px・L2 < 24px、ヒステリシス 15%。撮影の照準対象・ストーリーの個体は常に L0
- **BA**：主役 3D モデルの数と予算 → 暫定：最大 6 種、1 種 GLB 2 本で 55 KB 以内、LOD0 4,000 三角形（大型 6,000）・LOD1 600。試験は `turtle`・`aoriika` の 2 種
- **BB**：影を落とすもの → 暫定：植生は 30m 以内のセル、地形は今いるチャンクと隣、生き物は 0.6m 以上かつ 20m 以内。遠くの影が消えるのは、水中の霞で元々ほとんど見えないため
- **BC**：生成済みの種の保持数 → 暫定：120 種、90 秒以上離れている種から破棄（近づけばまた作る）
- **BD**：単一 HTML の大きさ → 暫定：上限 4,500 KB、設計値 4,400 KB。超えるときは主役 3D モデルの種数 → 写真魚の追加数の順で削る
- **BE**：植生（サンゴ）の LOD と影を Phase 8 に入れるか → 暫定：入れる。トラッカーの見出しは「魚・生物モデル」だが、項目 2「実機で動作が重い…軽くする」の対象で、計測では三角形の 7 割超が植生と影のため。サンゴの見た目（形・色）は変えない
- **BF**：`photoRange`（定義だけで未使用の項目）→ 暫定：LOD には流用せず、そのまま残す（消すのは Phase 12 の種データ整理のときにまとめて）
- **BG**：生成魚の三角形の増加 → 暫定：L0 は体長 0.4m 未満 1,500・以上 2,500 まで増やす（今は 464〜880）。L1・L2 で数を減らすので生き物全体の三角形は今より減る見込み（§3.5）
- **BH**：尾の振りの周波数 → 暫定：個体の速さから決め、見た目のため 0.6〜4Hz に収める（実際の小魚の 10Hz 超は震えに見えるため）。振幅は速さで 0.6〜1.0 倍、胸びれ型と止まり気味の個体は「振って滑る」

## 9. 実装手順（Claude 向け。§7.1 の S0〜S8 の中身）

### 9.1 S0 診断と画素数（`Game.ts`、`scripts/make-artifact.mjs`）

- `Game.ts` の `setPixelRatio` を `targetDpr()`（§6.3-⓪の式）に置き換え、`resize` と適応の両方で使う。適応の刻み 0.15、下げる：平均 > 36ms、上げる：平均 < 24ms が 3 回連続。
  - 実装時の補足（S0）：上限は従来どおり端末の `devicePixelRatio` も超えない（`min(devicePixelRatio, dprCap, sqrt(90万/面積))`）。下限は `min(上限, sqrt(30万/面積))`。調整値は `src/game/render.ts` の `RENDER`。
- `make-artifact.mjs` に第 3 引数 `--page` を足し、指定時は先頭に `<meta charset="utf-8">` と viewport の meta を付ける。`play.html` はこの出力をコピーする（RESUME.md と publish-artifact スキルの手順の記述も直す）。
- 診断表示：`?diag` か設定のデバッグ欄で、画面の隅に「fps・呼び出し・三角形・画素数（幅×高さ）・DPR・L0/L1/L2」を 1 秒ごとに更新。`__THREE_GAME_DIAGNOSTICS__` にも同じ値。

### 9.2 S1 軽量化（`environment.ts`、`flora.ts`、`scatter.ts`、`terrain.ts`、`creatures.ts`、`finds.ts`、`gearModels.ts`、`underwater.ts`、`Game.ts`）

- 影：`ScatterSet.update` で `castShadow = d < 30`。`terrain.ts` は今いるチャンクと隣だけ `castShadow`。`creatures.ts` の `castShadow` は `writeInstance` 時点の `minD < 20 && size >= 0.6`。影のカメラの範囲を 30m 四方に（`environment.ts` 63 行付近）。
- 植生の LOD：サンゴのビルダーに分割数の引数を足し、`ScatterSet` に `farGeo`/`farDist = 25` を足す（既存の `hiGeo`/`hiDist` と同じ書き方）。セルの大きさ 70 → 35m。
- フラグメント：`underwaterMaterial` に `mobile` の define（`UW_MOBILE`）を足し、コースティクスの 2 回目と影の PCF を切る。生き物の L1 用マテリアル（§9.5 で作る）は `UW_NO_CAUSTIC`。
- 小物：`finds.ts`／`gearModels.ts` の `chestModel` などを `mergeGeometries` で 1 メッシュに（材質ごとに頂点色で塗り分け）。60m より遠いと `visible = false`。光芒は 1 ジオメトリに結合。
- 破棄：`SpeciesRuntime` に `lastNear`、`buildMesh` の数を数え、120 を超えたら破棄（§6.3-⑥）。`dispose` 後は `rt.mesh = undefined` に戻すだけで、既存の遅延生成がまた作る。
- 間引き：`creatures.update` の個体ループで、`dPlayer > 25` は `(frame + i) % 2`、`> 45` は `% 4` のときだけ更新（dt に掛け算）。逃走中・追従中・`pin`／`stage`／`companion`・撮影対象は毎フレーム。
- 事前コンパイル：`startDive` の暗転中に、その地点の種類のマテリアルを並べたダミーのシーンを `renderer.compileAsync(scene, camera)`。
- 実装時の補足（S1）。設計の数値はそのまま、コードに合わせて変えた点は次のとおり。調整値は `src/game/render.ts`（`SHADOW`・`FLORA_LOD`・`PROP_VIEW`・`KEEP`・`THIN`）。
  - セル：実際に使われていたセルは 40・32・30・48m で、既定の 70m は使われていなかった。「70 → 35m」は `min(指定値, 35)` にした。
  - 影の距離はセル内の株を囲む箱（原点＋2m）までの距離で判定する（< 30m）。遠景の簡易ジオメトリはセルの境界球までの距離で判定する（> 25m）。
  - 影の PCF はシェーダの define ではなく、スマホで `renderer.shadowMap.type = BasicShadowMap` にして切る。1 サンプルでは岩の斜面に縞が出たので、スマホだけ `shadow.bias = -0.003`・`normalBias = 0.12`。影の輪郭は固くなる（海藻の葉の影が岩にはっきり出る）。気になれば `Game.ts` の 1 行で PCF に戻せる。`UW_MOBILE` はコースティクスだけに使い、1 回にした分は強さを 1.2 倍。
  - L1・L2 のコースティクスなし（`UW_NO_CAUSTIC`）と `FISH_SCALES` の L0 限定は、L1・L2 を作る S5 で入れる。
  - 生成済みの種：生き物を持つ範囲（68m の箱）に 213〜353 種が入るので、「近くの種を全部作る」ままでは 120 以下にできない。メッシュを作るのは「描けるとき」（描画の打ち切り距離の 1.1 倍以内。視界の前を先に、背後は保持数が 120 未満のとき）に変えた。個体の動き（シミュレーション）はメッシュがなくても今までどおり進む。
  - 間引き：飛ばしたフレームの dt はためて次の更新で渡す（上限 0.2 秒）。毎フレーム更新するのは、攻撃中・警戒中・餌に寄っている・見張り中・群れの現在の対象・撮影の照準・つかんでいる個体・逃げ始める距離内。
  - 事前コンパイル：代役のメッシュ（シェーダの組み合わせごとに 1 つ）を作って残し（破棄するとプログラムも消えるため）、`compileAsync` の後に 1 回だけ描いて影の深度シェーダも作る。深海の噴出孔の光は表示・非表示で光源の数が変わるので、上級ダイブ（ADS）では両方をコンパイルする。暗転は最長 2.5 秒。
  - 小物：宝箱は 60m より遠いと描かず、視錐台カリングも有効にした。拾い物の光芒（スプライト）は 60m でも消さない（本体だけ消す）。

### 9.3 S2 テクスチャ（`scripts/prep_pbr.py`、`src/render/baked.ts`）

- 再圧縮の設定を `prep_pbr.py` に引数で足す（品質・形式）。比較画像（§10.3）で劣化が見えたら 1 枚ずつ品質を戻す。
- 実装時の補足（S2）：`prep_pbr.py --recompress <元のファイルのフォルダ>` を追加し、13 枚を再圧縮した（JPEG q75、WebP q85・アルファ q75）。ゲームの画面（砂地・サンゴ礁・岩礁・沈没船・遺跡）で劣化は見えないので、品質は戻していない。テクスチャ単体の拡大では法線マップの細部がわずかになめらかになる。
  - 結果は 2,001 → 1,394 KB（base64）で、§6.4 の上限 1,250 KB に約 140 KB 届かない。`sand.webp` は「非可逆でない」前提で約 120 KB を見込んでいたが、実際は色がすでに非可逆（187 KB）でアルファが可逆（170 KB）だったので、349 → 263 KB にとどまった。
  - 法線マップの WebP は、ファイル名・拡張子を変えないので試していない（JPEG のまま）。
  - 残りを詰める案（未実施）：アルファ品質を下げる、法線 JPEG・WebP の品質をさらに下げる、WebP に置き換えて import を直す。いずれも S6 で全体の大きさを見て決める。

### 9.4 S3 泳ぎ（`creatures.ts` `makeMaterial`／`writeInstance`、`species2.ts` の `B`）

- `aSwim` の `InstancedBufferAttribute`（`def.count × 4`、`DynamicDrawUsage`）を `buildMesh` で付け、`writeInstance` で書く。`Agent` に `swPh`・`flPh`・`glide`・`prevYaw` を足す。
- 頂点シェーダの `vertexBody` を §4.2 の「背骨の線で曲げる」に書き換える（`BEND_Y` の分岐は残す）。振幅分布は `swimMode` ごとの 3 係数を uniform `uSwimA`（vec3）で渡し、波長・尾の振幅も uniform。
- `B` の各体型に `swimMode` の既定値を足す。個別定義の魚は kind・体型・`size` から決める関数 `swimModeOf(def)`。`def.swim` がある種は今の値を「周波数の下限・振幅の倍率」として読み替える（極端な値の種だけ目視で確認）。

### 9.5 S4 生成モデル v2（`models.ts` `buildFish`、`paint.ts`、`species2.ts`、`creatures.ts` `buildGeometry`）

- `FishShape` に `wPeak`・`pedW`・`xs`・`xsTop`・`xsBot`・`keel`・`mouth`・`scaleN` を足す（すべて省略可）。`buildFish(s, detail: 0 | 1)`：detail 1 は L1（rings 8・segs 12、ヒレの格子を 2 段、目を省く）。
- ヒレを格子で作る関数 `finGrid(outline, rows, cols)` を新設し、`flatPoly` を使っている尾・背・臀・胸・腹を置き換える。`thickFin` はそのまま使う。
- `aAO` 属性を足す（§5.2）。`ATTRS` に追加し、`finalize` で全パーツに付ける。
- `paint.ts`：ぼかし・側線・ヒレの縁と筋・α の sheen。`Look` に `lateral`・`finEdge`・`sheen` を足す。
- `buildGeometry` は L0 と L1 の 2 つを返す。

### 9.6 S5 LOD（新規 `src/life/impostors.ts`、`creatures.ts`）

- §1.3 のとおり。L1 の InstancedMesh は L0 とマテリアルを共有、`count` を別に持つ。アトラスの共有 InstancedMesh は 1 つ、インスタンス属性 `aCell`（アトラスのコマ番号）と `aSwim`。

### 9.7 S6 写真魚（`scripts/photo_fish.py`、`src/life/photoFish.ts`）
